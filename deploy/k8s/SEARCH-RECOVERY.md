# Search recovery after an uncertain index swap

The primary data is Strapi's database, not Meilisearch. The current `mizuki/shirone-search` deployment is a **single replica** with the Meilisearch data on its own `emptyDir`; its second container restores the restricted keys. The CMS must also be a single writer. An uncertain swap deliberately retains `posts_rebuild` and blocks further rebuilds: do not delete that staging index while the old writer or a swap task may still be running.

For this exact architecture, recovery can instead discard the **whole rebuildable search store**, after fencing both processes. This briefly makes CMS editing and search unavailable; it does not modify the database, uploads, or old-site data. Search must fail closed until the readiness marker appears in the new complete index. Do not use this procedure if search data is persistent, more than one writer or replica exists, an additional search writer is present, or the key reconciler is missing. Review live Deployment/Pod UIDs and resource versions rather than trusting old receipts.

1. Inspect `shirone-cms` and `shirone-search` Deployments, replicas, Pod owner UIDs, labels, `data` volume and the `restricted-key-reconciler` container. Confirm that the search volume mounted at `/meili_data` is an `emptyDir`, no other writer or active operator can change it, and no HPA will change these replicas. Record both Deployment UIDs, current replica counts and rollback details. Confirm current CMS and search Pod UIDs.
2. With UID and current resourceVersion tests in a Kubernetes JSON Patch, scale `shirone-cms` from 1 to 0. Wait until **all** Pods owned by that Deployment have terminated; stopping HTTP traffic alone is not a fence. If the patch or wait is uncertain, stop and inspect; do not continue assuming the writer stopped.
3. With the same UID/resourceVersion preconditions, scale `shirone-search` from 1 to 0. Wait until **all** of its Pods are gone and verify the old Pod UID no longer exists. Only then has the old Meilisearch process and its asynchronous swap queue ceased, and its Pod-scoped `emptyDir` been discarded. Never remove a directory on a node or delete a PVC as a substitute.
4. Guardedly scale search back to 1. Wait for the replacement Pod to be Ready, verify its UID differs, verify the reconciler reports restricted keys ready, and check the CMS deployment is still fenced. Restore CMS to 1 using its reviewed Deployment UID and fresh resourceVersion; wait for rollout. The CMS notices that the new index has no readiness marker and rebuilds from currently published content.
5. Poll the public search API until it responds successfully, then search for representative published Chinese text and confirm draft, encrypted, withdrawn and deleted articles are absent. Check site/API health and logs. Record completion. If it does not recover, keep the current evidence and diagnose; never repeatedly reset a non-empty index without understanding why.

If a step fails after a scale-down, the affected Deployment may intentionally remain at zero. Inspect UIDs, replicas, Pods and the current failure before restoring it; use fresh resourceVersion and UID tests, and do not re-run a stale patch. A running CMS retains an in-process `uncertainSwap` flag, so replacing the search Pod without also restarting the CMS is insufficient in that case. An independently restored search store or different writer topology requires its own recovery procedure.

The Ansible project provides `recover_shirone_search.yml`; its versioned source is `deploy/ansible/search-recovery.yml` and it invokes `deploy/tools/recover-search-index.py`. It defaults to a read-only inspection and server-side dry-run. Set `SHIRONE_WORKSPACE` to the repository checkout and supply freshly reviewed `recovery_cms_uid` and `recovery_search_uid`. Execution additionally requires `recovery_apply=true` and `recovery_confirm=discard-rebuildable-search-index`. The operator must independently verify that no other writer or operator can write to the search service: deployment, Pod, HPA and emptyDir checks alone cannot prove this. Never force-delete a Pod or use this procedure while a workload node is unreachable: a deleted API object does not prove its old process has stopped. The script requires the old workload nodes to remain Ready with unchanged node UIDs, fences CMS first, waits for owned Pods to disappear, fences search, verifies new Pod UIDs after restoring search then CMS, and stops on uncertain state. Node readiness is an additional check, not physical fencing of a partitioned node. A successful run must still be followed by verification of reconciler logs, the readiness marker, real published Chinese search and draft/withdrawn/deleted exclusion as described above; Pod readiness alone is insufficient.

The Kubernetes scaling and replacement sequence was rehearsed on 2026-11-02 in a unique, disposable namespace using synthetic sleeping containers with the same selectors, replica strategies, search container names and emptyDir mount. The default preview and explicit apply both succeeded, the old Pod UIDs disappeared, the replacement Pod UIDs differed, and the temporary namespace was deleted. No production Deployment was scaled. This test exercises Kubernetes guards and fencing; it is not a Kubernetes-level Meilisearch swap or a production database test.

`MEILI_DISPOSABLE=yes MEILI_TEST_IMAGE=<local-image> node deploy/tests/meili-uncertain-recovery.cjs` tests a real isolated Meilisearch: it sends a swap, simulates the response being lost, proves staging is retained and retries halt, then replaces the search process with an empty store and starts a fresh writer, which rebuilds a published Chinese document. It does not itself test Kubernetes scale operations, production credentials, CNPG, or restore of primary data. `deploy/tests/strapi-search-e2e.cjs` separately exercises empty-store key recreation and automatic recovery with real disposable Strapi and SSR containers.
