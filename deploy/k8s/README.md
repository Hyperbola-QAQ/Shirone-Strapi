The checklist and dated checkpoints below are historical migration records, not assertions of current state or instructions to replay provisioning. Recheck live resources and consult current Ansible entrypoints before changes. At the time of the original review the checklist was:

1. Use the existing SSH user kubeconfig on `imini` for read-only cluster checks; do not copy or print it. A fresh observation on 2026-10-30 found three Ready nodes, Mizuki 2/2, both routes accepted with resolved references, and CNPG 3/3 healthy. The formal Ansible inventory still requires a Vault credential not yet found. Recheck state and schedulable capacity at deployment time.
2. Build and test the SSR and CMS images and select a compatible pinned Meilisearch image. Mirror through the configured domestic/cluster registry first and retain immutable digests. Confirm actual runtime env contracts, UID/GID, writable paths and dependency-aware readiness; TCP readiness here proves only that a port accepts connections.
3. Provision a dedicated Strapi PostgreSQL database and restricted role through the cluster's managed mechanism; never reuse a database that belongs to another application. Put `DATABASE_HOST`, `DATABASE_PORT`, `DATABASE_NAME`, `DATABASE_SSL`, `APP_KEYS`, `API_TOKEN_SALT`, `ADMIN_JWT_SECRET`, `TRANSFER_TOKEN_SALT`, `JWT_SECRET`, `ENCRYPTION_KEY`, `MEILI_ADMIN_KEY` and `INTERNAL_RENDER_TOKEN` in the protected `shirone-cms` Secret. The database username and password come separately from `mizuki/shirone-cms-db`, which must match `databases/shirone-cms-db`; no password is provided by these manifests. The actual CMS config is authoritative.
4. Prepare `shirone-uploads` and `shirone-search` PVCs with verified permissions and recovery; choose the storage provider based on Meilisearch's supported filesystem semantics. Existing `nfs-ha` is asynchronous and its default reclaim policy deletes data; neither replication nor `Retain` substitutes for verified backups. Meilisearch is a rebuildable index, but Strapi uploads and PostgreSQL are primary data and require a tested restore.
5. Create `shirone-search` Secret containing `MEILI_MASTER_KEY` and `shirone-ssr` Secret containing `STRAPI_API_TOKEN`, the matching `INTERNAL_RENDER_TOKEN`, a server-only shared `PROTECTED_MEDIA_SESSION_SECRET` of at least 32 random bytes, and a search-only `MEILI_SEARCH_KEY`. Finalize server-only search access and least-privilege keys; do not expose the master key to browsers. Verify access control and network policies, and decide the secured CMS admin entrypoint before adding a route.
6. Add a narrow managed Ansible entrypoint, syntax-check and preview it; validate uploads, publication, search synchronization and restart/restore without touching production routes. Inspect the existing route and certificate. Only then switch the `mizuki` service/HTTPRoutes to the verified SSR backend, preserving tested rollback to the existing nginx Deployment and content PVC. Check route Accepted and ResolvedRefs, actual page body and assets, not HTTP status alone.

The currently archived `k8s/httproute.yaml` references the shared Higress gateway and `mizuki` Service; runtime state and source may have changed. Do not apply archived resources blindly.

## Media authorization boundary

The public admin hostname uses an allowlist of management routes and an ingress policy scoped to the Higress gateway. Do not route the CMS content API or `/uploads/` directly to CMS: both site and admin hostnames send uploads to SSR. SSR authorizes anonymous requests against current published content references; password-protected content additionally requires a valid short-lived media session. On the admin host only, an encrypted, host-only capability is checked with Strapi's active administrator session and upload permissions before private media is served. Do not cache a positive authorization past content revocation.

The existing Higress Pods use host networking, so cross-node traffic to the CMS has a node IP rather than a selectable Pod identity. `cms-gateway-nodes.yaml`, installed using `allow-cms-gateway-nodes.yml`, additionally allows only TCP 1337 from trusted control-plane addresses `192.168.86.11/32` and `192.168.86.21/32`. This is a node trust boundary: other processes on those two hosts can also access the CMS, including its direct upload endpoint. Other nodes and unrelated non-host-network Pods remain denied; verify this after topology or policy changes.

## Create-only database credential transaction candidate

`deploy/ansible/manage-db-credentials.yml` and the Ansible source copy `manage_shirone_db_credentials.yml` invoke `deploy/tools/db_credential_kubectl.py`. The default action is a non-mutating preview. Explicit `init` initializes an already existing owner-only 0700 stage directory with a 0600 persistent credential and transaction journal. Explicit `apply` requires a reviewed CNPG Cluster UID and both Namespace UIDs; the real `databases`/`mizuki` pair additionally requires `shirone_allow_production=true`. The two immutable basic-auth Secrets have the same strong generated credential and a shared transaction annotation; data travels only via process stdin and is not logged. Kubernetes writes are create-only. `--check` never initializes or applies.

The protected stage is the recovery source and must be retained securely outside transient `/tmp` for real use, with an independently verified recovery and rotation process. Pending states are durably recorded before remote requests; timeout, unknown response, mismatched UID/content or an unexpected pre-existing Secret leave the transaction held. No automatic re-generation, overwrite, cleanup, or retry is provided. A pending state needs an explicit reviewed operator recovery protocol; simply waiting or finding a process exited does not prove an in-flight API request could not still complete.

An isolated test used six randomly named disposable namespaces on the existing cluster with synthetic credentials: direct and Ansible-wrapped initialization, `--check`, apply, repeat verification and an injected lost acknowledgement all passed; the test checked namespace UID and ownership label before deletion, and all test namespaces were confirmed deleted. `deploy/tests/credential-k8s-check.py` can repeat this only with an explicit opt-in and reviewed Cluster UID. It creates and deletes only its own uniquely named test namespaces; it does not create the production Secrets.

These tests do not establish production safety. The lock coordinates only processes sharing the same trusted local stage and filesystem, and namespace verification followed by a Secret create is not a cross-object atomic transaction. Parent directories, node trust, independent credential recovery, operator fencing and pending-state recovery must be reviewed before production; no role or database is applied by the credential tool.

A pending credential transaction can be advanced with the explicit `resolve-present` action **only** when the operator has independently fenced the previous executor and all outstanding API requests, and both live object identities are reviewed. The tool takes a fresh read and accepts only the exact immutable Secret carrying the transaction annotation and matching credential; an absent or mismatched object remains HOLD. It does not create a Secret during recovery. The attestation flag records an operator decision; the code cannot prove network fencing or make cross-namespace actions atomic. Once the journal reaches `db_verified`, a separate explicit apply can create the second Secret; for `creating_cms`, successful resolution reaches `complete`. Never invoke this recovery based solely on a timeout or vanished local process.

`deploy/tools/db_credential_replicate.py` creates/compares create-only copies of the immutable credential source on imini and laiku under each user's `~/.shirone-strapi/credential-recovery/credential.json`. Directories are 0700, files 0600, SSH carries the JSON on stdin, and no credentials appear in command arguments or logs. Existing mismatching copies cause HOLD; a retry never overwrites a copy. The Ansible credential entrypoint verifies both copies before a production `apply`; explicit `replicate` also requires the production flag. The source must be stored on a separate local durable filesystem, not `/tmp`. The remote files are protected by Unix permissions **but are not encrypted separately at rest**; both nodes and their administrators must be trusted, and copies do not protect against a shared site compromise. The changing journal is deliberately not replicated, so recovering after losing the controller still requires independent reconciliation of live object UIDs, pending requests and the original transaction ID. These copies are not a database or upload backup.

A synthetic source was copied to disposable per-test private directories on both nodes. Repeating with the same source was idempotent, and attempting a different source failed without overwriting; disposable files were removed. Repeat only with `SHIRONE_ALLOW_DISPOSABLE_SSH_TEST=yes python deploy/tests/credential-replica-check.py`. The recovery copy mechanism itself has not been exercised with production credentials.
